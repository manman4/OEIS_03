# A346216: Ulam数の10の整数乗番目

初期値1,2の [Ulam数 A002858](https://oeis.org/A002858) を順番に計算し、[A346216](https://oeis.org/A346216) の値を求める。Philip GibbsとDonald Knuthのアイデアを参考にした新規実装。01と02はそれぞれ単独のC++ソースでビルドできる。

| 版 | 計算・保存の違い | 説明 |
| --- | --- | --- |
| [346216_01.cpp](346216_01.cpp) | 検索範囲不足や257種類目の圧縮パターンでは停止。標準出力は項番号付きCSV | [README_01.md](README_01.md) |
| [346216_02.cpp](346216_02.cpp) | 検索範囲不足を全探索で補い、辞書外のパターンも保存。b-fileと終了JSONを自動保存 | このREADME |

以下の実行方法と実装の説明は02を対象とする。

```math
a(n)=U_{10^n},\quad U_1=1,\quad U_2=2
```

各候補整数を飛ばさず、異なる過去の2項の和として表せる組がちょうど1組ならUlam数とする。経験的な剰余分布は検索と保存量の調整に使い、必要な検索範囲が欠けた場合は全探索で補う。圧縮辞書に収まらないパターンも元のbitで保存する。

## ビルドと実行

以下は、このREADMEがあるディレクトリをカレントディレクトリとして実行する。C++17、128 bit整数を扱えるコンパイラ、64 bitのPOSIX環境が必要。検査スクリプトにはPython 3と標準ライブラリを使う。Pythonは通常の計算には不要である。

macOSでのビルド:

```sh
/usr/bin/xcrun --sdk macosx clang++ -std=c++17 -O3 -Wall -Wextra -Wconversion -Wshadow 346216_02.cpp -o ulam02
```

小規模な確認。b-fileの入力・生成を使わず、候補120,000まで独立オラクルと比較する。検査スクリプトも同梱のb-fileには依存せず、保存検査用のb-fileは一時ディレクトリへ自分で作成する:

```sh
./ulam02 --ram --terms 10000 --verify-until 120000 --report 0 --no-bfile --no-summary
python3 verify_02.py
python3 verify_summary_02.py
```

100億項を計算する場合の実行例。上の計算記録は、同じ02の実行ファイルとこの項数・キャッシュ設定を使い、出力先を指定してユーザーが実行したもの:

```sh
./ulam02 --terms 10000000000 --disk cache_346216_02.bin --cache-mib 8 --report 10000000 --seconds 0
```

時間制限はない。通常の作業表は初期容量約7.78 GBの論理サイズとなり、例外保存用の追加容量が必要になる場合もある。`--disk` は存在しない新しいファイル名を指定する。既存ファイルは上書きしない。

標準設定では、存在しない `b346216.txt` を自動作成して節目を書き、同じ行を標準出力にも表示する。`--bfile FILE` で保存先を変更できる。添字はA346216の添字であり、100億項が確定すると `10 135174535215` の行になる。進捗と最後のJSONは標準エラーへ出る。`eta_seconds` は開始からの平均速度による残り時間の予測であり、時間制限ではない。

標準出力・標準エラーをb-file自身や同じinodeを指す別名へリダイレクトしない。引数が不正な場合、同一ファイルの保護より前に診断が書かれる未修正の問題がある。シェルの `>` による実行前の切り詰めも防げない。詳しくは [AUDIT_02.md](AUDIT_02.md) を参照。

剰余の境界そのものは例外に数えず、初期値1,2も集計に含む。個々の例外の値や項番号の一覧は保存しない。剰余の例外、圧縮辞書外の保存、全探索への切り替えは別の事象である。

最後のJSONは同じディレクトリの一時ファイルへ書き、同期後に名前を置き換える。同名のJSONは最新の記録になる。計算開始後の `Ctrl+C`、SIGTERM、時間・候補値上限の停止でも、その時点の統計を保存する。引数解析や保存先の準備の失敗、保存媒体の故障、SIGKILL、電源断では今回のJSONを保存できないことがある。

b-fileとJSONはファイルロックで協調する他の書き込みを拒否する。以前の計算で作成したb-fileが存在する場合は、初めから再計算して保存済みの行と照合し、新しい節目だけ追記する。既知の値を探索の枝刈りに使わない。保存済みb-fileより小さい項数で試す場合は `--no-bfile` または別の保存先を使う。

作業表は再開用のチェックポイントではない。辞書、部分ブロック、検索木、最近の項はRAMにあり、b-fileやJSONだけから直前の計算状態に戻る機能もない。

## 高速化と正確性

使用する剰余は整数で計算する。比は起動時に固定し、自動更新しない。

```math
p=856371966,\quad q=350477575,\quad r(x)=qx\bmod p
```

この整数比は、Gibbs・McCranieの [2017年の論文の3ページ](https://vixra.org/pdf/1711.0134v2.pdf#page=3) にある計算用の有理近似である。λの厳密値として証明されたものではない。

各候補までの所属表が正しいと仮定すると、次の理由で判定に必要な組を失わない。

1. 剰余が中央の半分に入る候補では検索木を使う。この範囲では以下の代表加数の剰余または補剰余は半分より小さく、それぞれ低い側・高い側の対応する木に属する。和が候補 $`u`$ なら、剰余の和は $`r(u)`$ または $`r(u)+p`$。前者は小さい剰余が $`r(u)/2`$ 以下、後者は小さい補剰余が $`(p-r(u))/2`$ 以下にある。等しいキーでは数値の小さい加数だけを代表とし、同一項同士の和と同じ組の重複を除く。
2. 各検索木は `cutoff` 未満のキーの既存項を全て保存する。経験的な保存条件や容量で項を省くときも、`cutoff` を下げてその条件を保つ。2組に届かず検索上限が保存範囲に達した場合は、部分検索の数を捨て、全探索で数え直す。
3. 最近の項の検索は、候補の半分より大きい加数を降順に一度ずつ調べる。窓が不足すれば、未検査の直前から同じ全探索を続ける。
4. 全探索は剰余や分布による制限を使わない。異なる2組が見つかれば一意でないことが確定し、0組・1組なら必要な範囲を調べ終えて判定する。
5. 共通の18 bitパターンは255種類までを1 byte符号で保存する。収まらないパターンは元のbitで保存し、所属情報を失わない。候補の途中の部分ブロックもRAMから正確に参照する。

初期値1,2から帰納的に候補を判定する。この説明は形式検証ではなく、以下の試験と実装の不変条件による確認である。

剰余分布の偏りによって多くの候補を少数の加数検査で確定できることは、速度に関する経験的性質。今回の100億項の記録では、候補1個当たり平均約5.68回の加数検査だった。18 bit圧縮は保存量を減らす役割であり、全範囲での線形時間や今後の同じ速度を保証するものではない。

## 検証記録と制限

通常版とUBSan・bounds検査・libc++のextensive hardening付きの版で、独立した組和列挙、候補3から120,000までの全判定、意図的な保存範囲不足と辞書外保存、RAMとSSDの一致、4 GiB超の位置、ファイルの衝突・ロック・中断・保存失敗を検査した。

補助検査では全262,144種類の18 bitパターン、全探索298,597ケース、検索木12,642ケース、整数比など222設定も比較した。最新の検査用ソースとログは [results/verification/](results/verification/)、対象ソースのハッシュと設定は [metadata.json](results/verification/metadata.json) にある。検査用コードは通常の計算の依存ファイルではない。01・02を独立した公開用ディレクトリから再ビルドし、READMEの小規模実行と通常版・検査付き版の基本検査を実行した記録は [publication_checks.json](results/verification/publication_checks.json) にある。 b-fileを同梱しないコピーからのビルド・基本検査と、02の初回保存も確認した。

UBSan付きで基本検査を実行する場合:

```sh
/usr/bin/xcrun --sdk macosx clang++ -std=c++17 -O1 -g -Wall -Wextra -Wconversion -Wshadow -fsanitize=undefined,bounds -fno-sanitize-recover=all -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_EXTENSIVE 346216_02.cpp -o ulam02_ubsan
python3 verify_02.py ./ulam02_ubsan
python3 verify_summary_02.py ./ulam02_ubsan
```

Clangの静的解析は指摘なし。ASanは最小プログラムでもランタイム初期化に失敗したため、ASan検査を通過したとは扱わない。引数解析時の診断とb-fileが同じファイルの場合の問題は未修正で、[監査報告](AUDIT_02.md) に再現コードと記録を残している。

C++実装全体の形式検証、100億項全体の独立検算、電源断、媒体のbit破損、ロックを無視する他プロセスの編集は未検証。検出した資源不足やI/O失敗は非完了として扱う。
